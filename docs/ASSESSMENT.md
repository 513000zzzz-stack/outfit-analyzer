# 第三阶段考核验收与录屏

考核的核心证据是一张照片在 Linux 服务器上的完整处理过程。你能说明浏览器、后端、队列、数据库和两个分析模块各负责什么，也能指出结果差异来自哪里。

## 逐项验收

- [ ] **复用第二阶段成果**。同一张图同时进入 YOLO 与豆包。结果页左侧显示检测框、色卡或颜色统计，右侧显示豆包对服饰与搭配的描述。说明 YOLO 使用训练权重与显式颜色规则，豆包根据整张图生成文本分析。
- [ ] **Python Web**。展示 Streamlit 的登录、上传、进度、并排结果和历史。说明表单文件如何进入 FastAPI 的 `POST /api/analysis/create`，任务编号怎样用于后续查询。
- [ ] **SQLAlchemy 与 PostgreSQL**。上传后新增记录，从历史中查到它，编辑备注后刷新确认更新，再删除一条已结束的演示记录。正式录屏所用的对比记录可以保留。
- [ ] **身份认证与 JWT**。用两个演示账号分别登录，在第二个账号的历史中确认看不到第一个账号的记录。解释登录校验后服务端签发令牌，后续接口从请求中识别用户，查询和修改时还要检查记录归属。
- [ ] **Redis 与异步任务**。提交后关注排队或处理中状态，同时观察 Worker 日志出现相应任务。生产者是 FastAPI，消费者是 Worker，Redis 负责传递任务，结果由数据库和共享文件保存。图片太小、执行太快而跳过排队状态时，可以用日志解释这一步。
- [ ] **Linux、Docker 与 nginx**。录下 SSH 进入服务器、`pwd`、项目目录、`docker compose ps`、必要的 API/Worker 日志，以及通过 nginx 打开的页面。解释镜像是运行环境模板，容器是运行实例，Compose 配置服务如何连接，数据卷负责保留历史和结果。
- [ ] **持久化**。完成一条记录后用 `docker compose restart` 重启服务，重新登录并打开该条记录，确认备注和结果仍可读取。
- [ ] **真实仓库与说明**。原 GitHub 仓库保留各阶段的实际提交。README 写清服务器环境、依赖、启动命令、权重准备和故障排查。补充自己的学习体会。

1. 展示 GitHub 仓库与相关提交。说明第二阶段的两个脚本分别解决什么问题。

4. 展示进度和 Worker 日志。结果出来后放大两栏，选一个你确实观察到的差异。比如检测框若包含皮肤或背景，框内的颜色比例会受影响；豆包输出则可以结合服装语义描述，也可能描述错细节。
5. 打开历史记录并修改备注。时间允许时切换另一个演示账号，演示历史隔离。

## 你要能讲明白的几件事

- **为什么应用要分成网页和 API？** 网页处理交互，API 处理身份、输入与业务规则。同一套接口可以用于网页和其他客户端。
- **为什么分析要放进队列？** YOLO 推理和外部 API 需要时间。提交请求可以很快返回任务编号，后台独立完成分析，网页用编号查询。
- **JWT 和用户权限有什么区别？** JWT 告诉后端请求属于哪个用户。后端还要用该用户身份核对分析记录的归属。
- **容器里为什么不用 `localhost` 找其他服务？** 容器有自己的网络环境。Compose 中，API 可通过服务名访问 PostgreSQL 和 Redis，页面通过服务名访问 API。
- **怎么区分问题出在 nginx、页面、API 还是模型？** 从浏览器是否能打开页面开始，再查 API 健康、任务是否入队、Worker 是否消费，最后看两套模型各自的错误。保留任务编号，方便把网页记录和日志对应起来。
